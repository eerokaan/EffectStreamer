# Application protocol v1

The browser-safe package entry exports `EVENTS`, `ACTIONS`, `validateScope`, `validateEnvelope`, and `validateManifest`. Node-only core supervision is a separate `@effectstreamer/common/core-process` entry.

Actions contain `{version:1,requestId,sessionId,participantId,attemptId,type,payload}`. Session and attempt are null before pairing; attempt is null between conditions. Participant membership is authenticated separately; identifiers in a message are never authentication. The coordinator validates the current view/attempt before applying an action. Snapshots include an increasing `revision`, stable participant/role, view data and setup/completion state.

Finalized recordings are announced in `mediaResult`, then requested by ID. Manifests contain only identity/track/source, canonical WAV filename/content type, byte length, SHA-256 and operational `complete`/`interrupted` status. No alignment/timing sidecars are produced. Transfer requests for retained earlier attempts may complete before the upload deadline, without advancing the current attempt. Only `{recordingId,sha256,stored:true}` from durable storage releases client data.

Remote `signal` envelopes use `est-event:signal` and carry `{connectionId:'uplink'|'downlink',generation,type:'offer'|'ice',sdp? ,candidate?,sdpMLineIndex?}`. The acknowledgement has the matching request ID and an optional `signal:{type:'answer',sdp}`; server ICE events include the participant/session/attempt/connection/generation scope. Null candidates mean end-of-candidates. Only the authenticated owner can signal its current connections. Remote media results carry the generation in their payload as well as the usual envelope scope.

Remote lifecycle commands are `prepareRemote` (two connections and authenticated ICE credentials), `startAudio` (activate recorders), `stopCapture` (end new microphone input), then `stopCore` (core drain finished; finalize recordings before closing peers). Both browser `mediaPrepared` results use `component:'remote'`; both `mediaStarted` results precede core content release. The worker's `audio.prime` command emits silence through the two internal sender branches while checking media readiness, then `audio.start` unmutes the microphone. It is only legal before starting a WebRTC sender. No experimental content is released merely by SDP or control readiness.
